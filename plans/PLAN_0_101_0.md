# v0.101.0 Implementation Plan

## Goal

Make relational multiplicity state durable and private, so the supported
INTERSECT/EXCEPT forms can remain incrementally maintained without exposing
branch counters or invisible rows through the stream-table relation. Keep
DISTINCT aggregate admission narrow and fail-closed until PostgreSQL equality,
NULL, deletion, memory, and numeric contracts are explicit.

## Work items

### REL-101-1 — Private set-operation state

- Add a versioned state relation keyed by stream table and semantic row
  identity.
- Store branch multiplicities separately from visible output rows.
- Populate the state during initial/full refresh and use it as the source of
  old branch counts during differential refresh.
- Emit only visible result-row changes to the stream table.
- Keep ALL forms multiplicity-correct rather than representing a count as a
  single visible row.

### REL-101-2 — Exact set semantics

- Prove `IS NOT DISTINCT FROM` equality for every set-operation output column.
- Cover `INTERSECT`, `INTERSECT ALL`, `EXCEPT`, and `EXCEPT ALL`.
- Test NULL values, duplicate rows, empty branches, last-occurrence changes,
  simultaneous branch changes, updates, and repeated retractions.
- Leave unsupported query shapes on FULL/AUTO rather than accepting an
  unproven delta.

### REL-101-3 — Shared private-state lifecycle

- Version the state identity and record generation/readiness metadata.
- Ensure ownership and search-path handling follow existing stream-table
  lifecycle helpers.
- Rebuild or invalidate state after query/identity changes.
- Clean state on drop and reinitialization.
- Cover restart, clone, upgrade, and failed-refresh recovery.

### AGG-101-1 — Narrow DISTINCT state path

- Admit only aggregate forms whose input equality and NULL behavior can be
  represented exactly with bounded private state.
- Preserve PostgreSQL DISTINCT semantics and keep vectorized admission
  fail-closed for unsupported forms.
- Enforce a memory bound and surface a clear fallback/error when it is
  exceeded.

### AGG-101-2 — Numeric contracts

- Use PostgreSQL's analyzed transition/output types for each supported
  aggregate overload.
- Test high-offset, low-variance inputs, repeated retractions, NULL
  transitions, and overflow.
- Avoid changing unrelated aggregate strategies.
